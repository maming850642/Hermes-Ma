# CLI 用户视角 UX 审计报告（2026-09-06）

> 结论先行：**我没有纸面审查，而是启动了独立进程真实使用了 CLI**（ConPTY 伪终端 120×30，四轮场景、约 10 次真实 LLM 往返、覆盖全部 20 个斜杠命令与所有交互提示符）。用户报告的三个痛点全部复现实锤，其中两个比想象中更严重：`/think on` 的"实时展示"是空头支票（代码里根本没有展开分支）；主提示符 Ctrl+C 会**随机**崩溃整个进程并打出裸 traceback。

## 一、怎么测的

- 用 winpty(ConPTY) 启动 `python main.py`（独立新进程，与 Web 会话隔离），真实终端渲染，键盘级输入（含 `\x03`(Ctrl+C)、`\x1b[A`(↑)、`\x1a`(Ctrl+Z) 等控制键）。
- 四轮场景：A 启动/B 帮助/C 对话与中断/D 推理开关/E 行编辑快捷键/F 全命令面/G HITL 审批/Z 退出；最后一轮专项 Ctrl+C/Ctrl+Z。
- 模型：`ornith-ai/Ornith-1.5-9B-GGUF`（隧道端点，单轮响应 15~60s）。每次交互均有屏幕帧与原始字节流留档。

## 二、P0 — 直接劝退用户的问题

### P0-1 主提示符 Ctrl+C 会随机崩溃整个 CLI（裸 traceback）

**实测**：同样的操作（提示符处有未发送文字时按 Ctrl+C）：
- 第 1 轮：进程直接死亡，屏幕打出完整 Python traceback（`KeyboardInterrupt` 在 `boot_ctx.teardown()` 的 logging 调用中引爆，`except Exception` 接不住）；
- 第 3 轮：正确显示"已取消（输入 /exit 退出）"。

两种结局都能出现 → **行为不确定的竞态**。根因链（run1 的原始字节流证实崩溃前连"已取消"都没打印）：ConPTY 下 Ctrl+C 有时以 `EOFError` 而非 `KeyboardInterrupt` 形态从 `Prompt.ask` 抛出 → 命中 `src/cli.py:1455` 的静默 `except EOFError: break` → 主循环退出 → teardown 期间挂起的 SIGINT 以 KeyboardInterrupt 引爆（`src/cli.py:1765`，只有 `except Exception`）。

**修法建议**：① `except (EOFError, KeyboardInterrupt)` 于主循环输入处统一按"取消/退出确认"处理，绝不静默 break；② teardown 外再包一层 `except BaseException`；③ 退出型 EOF（Ctrl+Z/Ctrl+D）应先问一句"确认退出？当前会话将保存"。

### P0-2 `/think on` 不展示推理——"实时展示"是虚假承诺（用户痛点"只能关不能开"的真相）

**实测（干净会话验证）**：`/think on` → 反馈"思考模式： 开（推理过程实时展示）"→ 提问后屏幕上仍然只有一行 `🧠 模型推理中…（推理内容已折叠）`，随后直接是答案。**推理正文从未展示**。

**代码证实**：`src/cli.py:1002-1005` 的 `reasoning_token` 分支无论 thinking 与谁都只打折叠提示，整个 CLI 不存在任何"展开推理"的显示路径。而 `/help`（`src/cli.py:202`）和开关反馈都承诺"推理过程实时展示/推理内容展开显示"。

连带问题：
- 默认（`/think off`）模型照样输出推理（服务端模板默认思考），于是用户第一次对话就看到"已折叠"却**无任何指引怎么展开**（而且实际上没法展开）；
- 术语割裂：提示说"推理"，开关叫"思考模式"，用户对不上号；
- `off` 也不真正关闭：`enable_thinking` 只是请求参数（`src/agent/agent_v3.py` extra_body 构造期固化），开关实为"显示开关"却假装是"模型开关"。

**修法建议**：① `reasoning_token` 增加 thinking=True 分支：推理正文流入 Live 面板（灰色/dim 样式区分正文），这是 Web 已有能力，CLI 对齐即可；② 折叠提示改为可操作：`🧠 推理已折叠，/think on 可展开`；③ /help 与开关反馈措辞改为与实际行为一致。

### P0-3 审批提示符吞掉一切输入 + 拒绝后无限审批循环

**实测（run2 G1）**：请求写文件 → 审批面板出现 → 输入 `yes` → `❌ 已拒绝执行 write_file：yes`（"其他任何输入 = 拒绝"陷阱实锤）。此后 CLI 卡死在审批 ping-pong 里：
1. 模型立即重试同一个 write_file → 又弹审批；
2. 我打的后续内容（新消息、`/compact`、`/resume`、`/reset`、`no`、`/foobar`…）**全部被当作"拒绝原因"吞掉**，用户永远回不到主提示符；
3. 模型被拒后**换 bash 工具用 shell 重定向绕过**（`echo "hello" > hello_ux.txt`）、再升级调 `request_human_approval` 元工具——每一步都弹新审批面板，9B 模型永不放弃；
4. 直接回车 = 拒绝（`default="reject"`，`src/cli.py:978`）。

**逃生门存在但无提示**：审批提示符处 Ctrl+C →"（审批输入已取消，本轮暂停在审批上）"（实测有效），但界面从未告诉用户。

**修法建议**：① 审批选项改为编号菜单（`[1]批准 [2]拒绝 [3]拒绝并不再询问本轮`），回车默认**不执行**也不算拒绝；② "其他输入=拒绝"改为"其他输入=拒绝，输入 ? 查看帮助"；③ 审批面板常驻一行提示：`提示：Esc/Ctrl+C 可暂停本轮回到主界面`；④ 拒绝同一工具 2 次后自动注入"用户已明确拒绝该操作，请勿再用任何工具重试（包括 shell 变体）"的系统提示。

## 四、P2 — 打磨项

- **行编辑键**：Ctrl+U / Ctrl+W 不可用——Ctrl+U 会把 `^U` 控制字符插进输入并随消息发给模型（实测 `/events` 里留有 `lloabc` 消息记录）。行编辑完全依赖 Windows 控制台宿主。
- **↑ 历史召回其实能用**（控制台宿主自带，实测召回成功），但 /help 无任何说明，且仅进程内有效、重启清零。低成本的胜利：文档写一句即可。
- **Ctrl+Z（Windows 传统 EOF）**：被当作字面 `^Z` 插入行内，回车后 `"\x1a"` 会被当消息发给模型（实测）。应显式处理为退出或忽略。
- **/help 表高于 30 行终端**：标题与 `/model` 行被顶出视野（实测）。可分两栏或压缩行高。
- 恢复会话时 assistant 工具调用消息只显示"（工具调用）"面板，无上下文。
- `show_session_history` 的 `/resume -a` 提示、`/resume` 选择器的"编号/n/p/q"提示、`/reset` 的确认——这些做得好，保持。
