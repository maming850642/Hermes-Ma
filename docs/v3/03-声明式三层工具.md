## 3.1 全景：三层架构

```
┌─────────────────────────────────────────────────────────────┐
│  Layer 1：静态定义（YAML → ToolSpec）                        │
│  ┌─────────────────────────────────────────────────────┐    │
│  │ tools/bash.yaml / create_mcp.yaml / ...（16 个）     │    │
│  │   name / description / parameters(JSON Schema)      │    │
│  │   runtime: { type: shell/python/mcp, ... }          │    │
│  │   side_effects: { destructive, writes_state, ... }  │    │
│  │   config_guard: shell_enabled                       │    │
│  │   se_evaluator / se_overrides（Layer 3 修正器）      │    │
│  └──────────────────┬──────────────────────────────────┘    │
│                     │ loader.load_tool_from_yaml             │
│                     ▼                                       │
│  ┌─────────────────────────────────────────────────────┐    │
│  │ ToolSpec（src/tools/schema.py）                     │    │
│  │   .to_openai()  → 给 LLM 看的 function JSON         │    │
│  │   .executor     → 给运行时用的执行器                 │    │
│  │   .side_effects → 给权限层看的行为画像               │    │
│  └──────────────────┬──────────────────────────────────┘    │
└─────────────────────┼───────────────────────────────────────┘
                      │ resolve_tools（config_guard 过滤 + MCP）
                      ▼
┌─────────────────────────────────────────────────────────────┐
│  Layer 2：权限决策（permissions.decide，详见 04 章）          │
│  decide(spec, args, ctx) → PermissionDecision               │
│    Layer 3 evaluator → 修正 destructive / force_deny        │
│    Layer 2 mode × destructive → allow/requireApproval/deny  │
└─────────────────────┬───────────────────────────────────────┘
                      │ allow
                      ▼
┌─────────────────────────────────────────────────────────────┐
│  Layer 3：执行（ToolExecutor.execute，3 种执行器）            │
│  ┌────────────┐ ┌──────────┐ ┌──────────────┐             │
│  │ShellExecutor│ │PythonExec│ │ McpExecutor  │             │
│  │(bash.yaml) │ │(复杂工具) │ │(MCP 动态)    │             │
│  └────────────┘ └──────────┘ └──────────────┘             │
└─────────────────────────────────────────────────────────────┘
```

## 3.2 ToolSpec —— 唯一的工具描述对象（取代 langchain BaseTool）

| | |
|---|---|
| **文件** | `src/tools/schema.py`（~173 行） |
| **取代** | `langchain.tools.BaseTool` / `@tool` 装饰器 |

### dataclass 字段（`schema.py:121-161`）

```python
@dataclass
class ToolSpec:
    # ─── 面向 LLM（to_openai() 直接吐 OpenAI function JSON）───
    name: str                         # 唯一名，MCP 用 mcp__<server>__<tool> 前缀
    description: str                  # 注入 LLM 的 function description
    parameters: dict[str, Any]        # JSON Schema dict（不经 Pydantic 转换）

    # ─── 面向运行时：执行 ───
    executor: "ToolExecutor"          # 执行器实例

    # ─── Layer 1：行为描述 ───
    side_effects: SideEffects = field(default_factory=SideEffects)

    # ─── Layer 3：动态修正器（可选）───
    se_evaluator: SideEffectsEvaluator | None = None     # Python 函数版
    se_overrides: list[SideEffectsRegexOverride] = ...   # regex 版

    # ─── 元信息 ───
    source: ToolSource = "yaml"       # yaml（内置）| mcp（动态发现）
    config_guard: str | None = None   # 需 getattr(settings, this_key, False) 为 True 才启用

    def to_openai(self) -> dict[str, Any]:
        return {"type": "function", "function": {...}}
```

> **V2 对照**：V2 用 langchain `@tool` 装饰器，靠函数签名（类型注解）+ docstring 自动生成 JSON Schema。问题：① schema 不可控（LangChain 的 `_create_subset_model` 遇到 MCP 的 `data` 字段抛 `KeyError`）；② 工具元信息（权限、执行方式）散落在代码各处（`_INTERRUPT_TOOL_NAMES` 硬编码集合）。V3 把工具完全声明化——YAML 定义 schema + 行为，一个 dataclass 承载一切。

### SideEffects —— 行为画像（`schema.py:42-67`）

```python
@dataclass
class SideEffects:
    destructive: bool = False       # ★ 唯一参与 Layer 2 mode 决策的字段
    writes_state: bool = False      # 改 agent 内部 state（todos/vfs/记忆），不参与决策
    network_access: bool = False    # 访问外部网络，不参与决策（plan 允许搜索）
    spawns_process: bool = False    # spawn 子进程/子 agent，不参与决策（plan 允许规划）
```

> **设计哲学**：「行为描述」≠「权限决策」。`destructive=True` 表示"我会改数据"，不表示"我要审批"——审不审批由 Layer 2 的权限模式基于这些标签决定。只有 `destructive` 参与 mode 决策；其他三个仅供日志/审计/UI。

### SideEffectsOverride —— Layer 3 的返回值（`schema.py:74-88`）

```python
@dataclass
class SideEffectsOverride:
    destructive: bool | None = None  # 覆盖 Layer 1 标签。None = 不覆盖
    force_deny: bool = False         # 硬底线：任何模式（含 full_access）都拒绝
```

> **典型用法**：`run_shell` 的 `destructive` 静态标签是 `True`（能力上限——能跑 `rm -rf`），但本次调用可能是 `ls`（实际无破坏）。Layer 3 evaluator 按 args 动态修正：`ls` → `destructive=False`，`rm` → 保持 `True`。

### SideEffectsRegexOverride —— regex 版修正器（`schema.py:94-110`）

```python
@dataclass
class SideEffectsRegexOverride:
    field: str                       # 要检查的参数名（如 "command"、"url"）
    patterns: list[str]              # regex 列表（任一命中即触发）
    override: SideEffectsOverride    # 命中后应用的覆盖
    reason: str = ""                 # 人类可读原因
```

> **典型用法**：`web_fetch` 的 SSRF 内网检测——`field="url"`，`patterns=[r"^https?://localhost", r"^https?://127\.", r"^https?://10\.", ...]`，命中 → `force_deny=True`。

## 3.3 decide() —— 三层叠加权限决策

| | |
|---|---|
| **文件** | `src/tools/permissions.py`（~195 行） |
| **取代** | 硬编码 `_INTERRUPT_TOOL_NAMES` / `BLOCKED` 集合 / `if name=="task"` 字符串拦截 |

> 权限决策是 HITL 系统的核心，**完整的机制详解（含 mode 切换、resume 重新求值）见 [04 章](04-异常式HITL与权限系统.md)**。本章只列函数清单。

### 求值顺序（`permissions.py:164-194`）

```
decide(spec, args, ctx)
   │
   ├─ 1. Layer 3：evaluate_layer3(spec, args, ctx) → SideEffectsOverride
   │     ├─ se_evaluator（Python 函数）优先
   │     └─ se_overrides（regex 列表）次之
   │
   ├─ 2. force_deny=True → 直接 deny（硬底线，任何模式）
   │
   ├─ 3. 修正后的 destructive：
   │     effective_destructive = override.destructive ?? spec.side_effects.destructive
   │
   └─ 4. Layer 2：evaluate_layer2(mode, effective_destructive)
         │  full_access    → allow
         │  before_changes → destructive ? requireApproval : allow
         │  plan           → destructive ? deny : allow
         ▼
         PermissionDecision(action, reason)
```

### 函数清单

| 函数 | 行号 | 说明 |
|------|------|------|
| `evaluate_layer3()` | `permissions.py:85` | 运行 Layer 3 修正器 |
| `evaluate_layer2()` | `permissions.py:122` | mode × destructive 决策 |
| `decide()` | `permissions.py:164` | 三层叠加入口 |

### 决策表（`permissions.py:22-27`）

| 模式 | destructive=True | destructive=False |
|------|------------------|-------------------|
| `full_access` | 放行 | 放行 |
| `before_changes` | **requireApproval** | 放行 |
| `plan` | **deny** | 放行 |

### PermissionDecision（`permissions.py:59-78`）

```python
@dataclass
class PermissionDecision:
    action: Action  # "allow" | "deny" | "requireApproval"
    reason: str = ""
    @property
    def is_allow(self) -> bool: ...
    @property
    def is_deny(self) -> bool: ...
    @property
    def needs_approval(self) -> bool: ...
```

| | |
|---|---|
| **基类** | `src/tools/executor_base.py`（`ToolExecutor` ABC，`executor_base.py:35`） |
| **Shell** | `src/tools/executors/shell.py`（`ShellExecutor`，`shell.py:208`） |
| **Python** | `src/tools/executors/python.py`（`PythonExecutor`，`python.py:43`） |
| **Mcp** | `src/tools/executors/mcp.py`（`McpExecutor`，`mcp.py:57`） |

> 2026-09：`FsExecutor`（7 个文件工具）已删除，文件操作统一走 ShellExecutor + `file-ops` 技能。

### ToolExecutor ABC（`executor_base.py:35-60`）

```python
class ToolExecutor(ABC):
    @abstractmethod
    def execute(self, args: dict[str, Any], ctx: ToolContext) -> ToolResult: ...
```

> 执行器是"配置对象"——YAML 加载时构造一次，多次 `execute`。`__init__` 参数来自 YAML 的 `runtime` 段。**权限决策在 `executor.execute()` 之前完成**（由 `ToolRegistryV3.execute` 调用 `decide()`），executor 只管"怎么执行"。

### resolve_workspace_root() —— 共享锚点（`executor_base.py:67-96`）

```python
def resolve_workspace_root() -> Path | None:
    workspace_root = settings.get("workspace_root")
    if not workspace_root: return None
    user_id = get_current_user_id()         # ★ contextvar
    root = Path(workspace_root) / "users" / user_id   # per-user 分层
    root.mkdir(parents=True, exist_ok=True)
    return root
```

`ShellExecutor` 用这个锚点当 cwd。未配置时返回 None（Shell 应被权限层拒绝）。读 `get_current_user_id()` contextvar——**同一个 contextvar 贯穿 shell / memory / bus 等子系统**。

### ShellExecutor（`shell.py:208-349`）

- **workspace 锚点检查**：None → 拒绝执行（防误伤宿主机）（`shell.py:231-235`）
- **Windows Git Bash 探测**：`_find_git_bash`（`shell.py:73-119`）PATH → 常见路径 → git.exe 反推；`_resolve_shell_program`（`shell.py:122-173`）进程级缓存
- **进程树杀**：`_kill_process_tree`（`shell.py:176-205`）—— Windows 用 `taskkill /T /F`，POSIX 用 `os.killpg`。解决 `subprocess.run(shell=True)` 超时只杀 `cmd.exe` 子进程成孤儿的问题
- **Popen + 手动 kill** 取代 `subprocess.run(timeout=)`（`shell.py:246-256`）
- **编码解码** `_decode_output`（`shell.py:44-65`）：UTF-8 → GBK → locale → replace
- **输出截断** `shell_max_output_chars`（`shell.py:323-326`）

> **Layer 3 的 `classify_command` 不在 shell.py 里**——shell 的 HITL 审批由 permissions Layer 3 的 evaluator（YAML 声明，loader 动态加载 `src.tools.shell_safety.classify`）处理。`ShellExecutor` 被调用时权限已全通过，只管执行。

### PythonExecutor（`python.py:43-92`）

- 服务 `web_fetch` / `web_search` / `task` / `compact_conversation` / `remember` / `use_skill` / `request_human_approval` / `write_todos` 等复杂工具
- importlib 延迟加载 `module.function`（`python.py:56-61`），注入 `ctx` 尾参
- **InterruptSignal 必须向上冒泡不能被吞**（`python.py:72-73, 78-79`）——`request_human_approval` 靠这个
- 返回值统一 `ToolResult`（str/dict 自动包装）

### McpExecutor（`mcp.py:57-124`）

- **per-server 锁串行化**同一 server 调用（防 stdio 响应错位）：`_server_locks` 注册表（`mcp.py:40-41`），`_get_server_lock`（`mcp.py:44-54`）
- 通过 event loop 线程 `run_coro` 调 `client.call_tool`，`with server_lock` 串行化

> **为什么 per-server 锁？** stdio transport 是顺序通信，多线程并发调同一 server 的多个工具会**响应错位**（A 的请求、B 的响应、JSON 解析错乱）。per-server 锁保证对同一 server 的调用串行。

### YAML 结构示例（`tools/bash.yaml` 节选）

```yaml
name: run_shell
description: |
  执行 Shell 命令。默认需人工审批；白名单命令（ls/cat/echo/git/...）自动放行。
parameters:
```

```python
def resolve_tools(ctx, settings, include_mcp=True) -> list[ToolSpec]:
    specs = load_builtin_tools()              # 16 个 YAML
```

```python
def _passes_guard(spec, settings) -> bool:
```

## 3.7 ToolContext —— 调用级上下文（双通道原则）

| | |
|---|---|
| **文件** | `src/tools/context.py`（~60 行） |
| **取代** | langchain `CallbackManagerForToolRun` |

### PERMISSION_MODE 常量（`context.py:28-32`）

```python
PERMISSION_MODE_FULL = "full_access"
PERMISSION_MODE_BEFORE = "before_changes"
PERMISSION_MODE_PLAN = "plan"
DEFAULT_PERMISSION_MODE = PERMISSION_MODE_BEFORE
```

### ToolContext 字段（`context.py:35-60`）

```python
@dataclass
class ToolContext:
    permission_mode: str = DEFAULT_PERMISSION_MODE   # 会话级，用户随时切换
    caller_context: str = "main"                     # main/employee/subagent
    progress_cb: Callable | None = None              # 进度回调
```

### 双通道原则（`context.py:6-16`）

| 通道 | 载体 | 内容 | 特点 |
|------|------|------|------|
| contextvars | `_current_user_id` / `_current_vfs` / `_current_depth` | 会话级**固定值**（同一次请求内不变） | 跨线程 `copy_context()` 自动传播 |
| ToolContext 尾参 | `permission_mode` / `caller_context` / `progress_cb` | 调用级**变化值**（不同工具调用可能不同） | 显式传参，不依赖线程 |

> **为什么分两通道？** user_id / vfs / depth 在一次请求内是固定的，用 contextvars 可以跨线程自动传播（`copy_context()`），避免每个函数都加 `user_id` 参数。但 permission_mode / caller_context 是调用级可能变化的（比如子 agent 继承父会话 mode 但 caller_context="subagent"），用显式尾参更清晰、不易出错。

## 3.8 工具执行流程（端到端）

从 LLM 输出 tool_calls 到结果回灌的完整链路：

```
LLM 输出（流式 accumulate 后）
   │ ai_msg.tool_calls = [{"id","type":"function","function":{"name","arguments"}}]
   │
   ├─ safe_parse_tool_args(arguments 字符串 → dict)         [02 章 §5]
   │
   ├─ 转 langchain AIMessage(tool_calls=[{id,name,args}]) 存入 state
   │
   ├─ registry.process_tool_calls(tool_calls, ctx, event_sink)
   │     │
   │     ├─ 过滤未知工具名
   │     ├─ _contains_approval_tool 预判（destructive 或有 se_evaluator → 串行）
   │     │
   │     ├─ 单工具 / 含审批 → _execute_serial（逐工具 _execute_with_timeout）
   │     └─ 多非审批 → _execute_concurrent（ThreadPoolExecutor + 每 worker copy_context）
   │          │
   │          └─ 每 worker: execute(spec, args, ctx)
   │               │
   │               ├─ coerce_args（轻量 JSON Schema 类型强转）
   │               ├─ decide(spec, coerced, ctx)             [04 章]
   │               │    ├─ deny → return ToolResult("错误：...")
   │               │    ├─ requireApproval → raise InterruptSignal ★
   │               │    └─ allow ↓
   │               │
   │               └─ spec.executor.execute(coerced, ctx)
   │                    └─ ToolResult(content, state_updates)
   │
   ├─ event_sink 推 tool_start / tool_end / todos_update
   │
   ├─ ToolMsg → 转 langchain ToolMessage 存入 state
   │
   └─ 合并 state_updates（todos / compact_requested）
        └─ compact_requested → _compact_messages
```

### coerce_args —— 轻量类型强转（`registry_v3.py:74`）

```python
def coerce_args(args, parameters) -> dict:
    # 按 parameters 的 JSON Schema type 声明强转
    # "60" → 60, "true" → True, "3.0" → 3
    # 缺必填项不抛（让 executor 自己返回友好错误）
    # 未知字段保留（宽松）
```

> **V2 对照**：V2 靠 langchain 的 Pydantic 校验 + 工具函数内的 `int(raw_timeout)` 防御性强转（散布在 3 个地方：`sub_agent.py:118`、`run_shell.py:138`、`tools_registry.py:596`）。V3 把类型强转收归到 `coerce_args` 一处，在 `decide()` 之前执行——保证权限层和执行层看到的参数类型一致。

## 3.9 完整样例：新增一个工具（端到端）

> 本节用一个真实案例——**`word_count` 工具**（统计工作空间内文件的行数/词数/字符数）——演示从零新增一个工具的完整流程。这个样例覆盖所有关键点：python 执行器、参数声明、per-user workspace 隔离、返回格式、权限标注。**可直接照抄运行**。

### 流程概览（3 步）

```
① 写 YAML（tools/word_count.yaml）       ← schema + side_effects + 执行器指向
② 写 Python（src/tools/word_count.py）    ← _execute_word_count 函数
③ 重启 worker                             ← loader 自动扫描 tools/*.yaml
```

**不需要改的**：`registry_v3.py`、`permissions.py`、`resolve.py`、`loader.py`、任何 `_INTERRUPT_TOOL_NAMES` 硬编码。`load_builtin_tools()`（`loader.py:183`）启动时扫描 `tools/*.yaml`，新文件自动被发现。

### 步骤 ①：写 YAML（`tools/word_count.yaml`）

```yaml
name: word_count
description: >
  统计工作空间内某个文件的行数、词数、字符数。
  路径必须以 / 开头（workspace 内绝对路径）。
  适用于需要评估文件规模、规划阅读策略的场景。

parameters:
  type: object
  properties:
    path:
      type: string
      description: 文件路径，必须以 / 开头（如 /notes/project.md）。
  required: [path]
  additionalProperties: false

runtime:
  type: python
  module: src.tools.word_count
  function: _execute_word_count

side_effects:
  destructive: false       # 只读统计，任何权限模式都放行
  writes_state: false
  network_access: false
  spawns_process: false
```

**逐字段说明**：

| 字段 | 作用 | 谁读它 |
|------|------|--------|
| `name` | 工具唯一标识（LLM 用它调工具） | `to_openai()` → LLM；`registry._specs` 查找 |
| `description` | 告诉 LLM 何时用这个工具 | `to_openai()` → LLM（决定调用准确率） |
| `parameters` | JSON Schema，声明参数类型 | `to_openai()` → LLM；`coerce_args` 强转依据 |
| `runtime.type` | 选哪种执行器 | `loader._build_executor` → Shell/Fs/Python/Mcp |
| `runtime.module` / `function` | python 执行器的入口 | `PythonExecutor` importlib 延迟加载 |
| `side_effects.destructive` | ★ 唯一参与权限决策的字段 | `decide()` Layer 2 |
| `side_effects.*` | 行为画像（日志/审计用） | 不参与决策，仅供 UI/日志 |

### 步骤 ②：写 Python（`src/tools/word_count.py`）

```python
"""word_count 工具 —— V3 PythonExecutor 入口。

签名约定（看 python.py:56-67）：
  - 参数名 = YAML parameters.properties 的 key，按位置传
  - 尾参 ctx=None（ToolContext，可选，本工具用不上）
  - 返回 str → PythonExecutor 自动包装成 ToolResult(content=str)
"""

from __future__ import annotations
from pathlib import Path

from src.tools.executor_base import resolve_workspace_root


def _execute_word_count(path: str, *, ctx=None) -> str:
    """统计文件的行数/词数/字符数。

    Args:
        path: workspace 内绝对路径，必须以 / 开头。
        ctx: ToolContext（尾参，可选，本工具不用）。
    Returns:
        格式化的统计结果字符串。出错返回友好的错误提示（不抛异常）。
    """
    # 1. 解析 workspace 锚点（per-user 隔离）
    #    resolve_workspace_root() 读 get_current_user_id() contextvar，
    #    返回 <workspace_root>/users/<uid>/，自动建目录。
    workspace = resolve_workspace_root()
    if workspace is None:
        return "错误：workspace 未配置，无法访问文件系统。"

    # 2. 路径安全：拼接到 workspace 内，防路径穿越
    #    去掉开头的 / 后拼接到 workspace 根
    rel = path.lstrip("/")
    file_path = (workspace / rel).resolve()
    try:
        file_path.relative_to(workspace.resolve())  # 边界检查
    except ValueError:
        return f"错误：路径越界，必须在工作空间内：{path}"

    # 3. 读文件（防御性：不存在 / 非文本 / 过大）
    if not file_path.exists():
        return f"错误：文件不存在：{path}"
    if not file_path.is_file():
        return f"错误：不是文件：{path}"

    try:
        text = file_path.read_text(encoding="utf-8")
    except UnicodeDecodeError:
        return f"错误：文件不是 UTF-8 文本：{path}"

    # 4. 统计
    lines = text.count("\n") + (1 if text and not text.endswith("\n") else 0)
    words = len(text.split())
    chars = len(text)

    return (
        f"📁 {path}\n"
        f"  行数：{lines}\n"
        f"  词数：{words}\n"
        f"  字符数：{chars}"
    )
```

**关键约定**（对照 `python.py:43-92`）：

| 约定 | 说明 |
|------|------|
| 函数名 | YAML 的 `function` 字段值，项目约定 `_execute_xxx` |
| 参数顺序 | = YAML `parameters.properties` 的声明顺序，按位置传 |
| `ctx` 尾参 | 可选，需要读 `permission_mode` / `caller_context` 时才用 |
| 返回 `str` | `PythonExecutor` 自动包装成 `ToolResult(content=str)` |
| 返回 `ToolResult` | 直接用（需要 `state_updates` 时，见下方变体） |
| 返回 `dict` | 自动包装（但 state_updates 不生效，需显式返回 ToolResult） |
| **不抛异常** | 出错返回友好错误字符串（让 LLM 自己决定下一步），不 crash agent |

### 样例变体：需要改 agent state

如果你的工具需要更新 agent state（像 `write_todos` 更新 todos、`compact_conversation` 发压缩信号），返回 `ToolResult` 而非 str：

```python
# src/tools/word_count.py 变体：把上次统计结果存入 state
from src.agent.tool_result import ToolResult

def _execute_word_count(path: str, *, ctx=None) -> ToolResult:
    # ... 同上的统计逻辑 ...
    stats = {"path": path, "lines": lines, "words": words, "chars": chars}

    return ToolResult(
        content=f"📁 {path}\n  行数：{lines}\n  词数：{words}\n  字符数：{chars}",
        state_updates={"last_word_count": stats},   # ← 合并到 state
    )
```

> ⚠️ **注意**：`_react_loop`（`agent_v3.py:490-495`）目前只合并 `todos` 和 `compact_requested` 两个 key。如果你新增别的 key（如 `last_word_count`），需要在 `_react_loop` 里加一行：
> ```python
> if "last_word_count" in state_updates:
>     state["last_word_count"] = state_updates["last_word_count"]
> ```
> 这是**唯一需要改 agent 代码**的情况——纯返回 str 的工具完全不用碰 agent。

### 样例变体：需要 Layer 3 动态权限

如果你的工具像 `run_shell` 一样，destructive 标签需要按本次参数动态修正（比如一个 `file_ops` 工具，`read` 时只读、`delete` 时破坏），加 `side_effects_evaluator`：

```yaml
# tools/file_ops.yaml（假设）
name: file_ops
description: 文件操作（read/write/delete）。
parameters:
  type: object
  properties:
    operation: { type: string, enum: [read, write, delete] }
    path: { type: string }
  required: [operation, path]
  additionalProperties: false

runtime:
  type: python
  module: src.tools.file_ops
  function: _execute_file_ops

side_effects:
  destructive: true          # 能力上限（能 delete）
  writes_state: false
  network_access: false
  spawns_process: false

# ★ Layer 3：按 operation 动态修正 destructive
side_effects_evaluator:
  module: src.tools.file_ops_safety
  function: classify_operation
```

```python
# src/tools/file_ops_safety.py
from src.tools.schema import SideEffectsOverride

def classify_operation(args: dict, ctx) -> SideEffectsOverride:
    """按 operation 修正 destructive 标签。

    签名约定：(args dict, ctx) -> SideEffectsOverride
    返回值：
      destructive=False → 降级（任何模式放行）
      destructive=None  → 沿用 YAML 静态值（这里是 true）
      destructive=True  → 强制保持
      force_deny=True   → 硬底线（任何模式拒绝）
    """
    op = args.get("operation", "")
    if op == "read":
        return SideEffectsOverride(destructive=False)   # 降级
    # write/delete：沿用 YAML 的 destructive=true
    return SideEffectsOverride(destructive=None)
```

### 决策树：destructive 怎么标？

```
你的工具会修改/删除用户数据吗？
├─ 否 → destructive: false
│        （任何权限模式都放行，如 word_count / web_search）
│
└─ 是 → destructive: true
         │
         ├─ 但有时只读（如 run_shell 的 ls）？
         │   └─ 加 side_effects_evaluator 动态降级
         │
         └─ 有绝对禁止的情况（如 fork bomb）？
             └─ evaluator 里 force_deny=True
```

权限决策表（`permissions.py:22-27`）：

| 模式 | destructive=true | destructive=false |
|------|------------------|-------------------|
| `full_access` | 放行 | 放行 |
| `before_changes`（默认） | **需审批** | 放行 |
| `plan` | **拒绝** | 放行 |

### 验证清单

新增工具后，用这 4 个问题自检：

| # | 问题 | 怎么验证 |
|---|------|---------|
| 1 | LLM 看得到这个工具吗？ | `/tools` 命令列出，或检查 `resolve_tools()` 返回的列表 |
| 2 | 权限决策对吗？ | 在 `plan` 模式下调它：destructive=true 应被拒绝，false 应放行 |
| 3 | contextvars 隔离对吗？ | 工具内调 `get_current_user_id()`，多用户并发应各自拿到自己的 uid |
| 4 | 并发安全吗？ | 如果工具可能被并发调用（多 tool_calls 同批），确保无共享可变状态，或用锁 |

### 常见陷阱

| 陷阱 | 解法 |
|------|------|
| YAML 改了不生效 | `load_builtin_tools` 有缓存（`loader.py:183`），重启 worker |
| 新 state_updates key 不生效 | `_react_loop` 只合并 `todos` / `compact_requested`，新 key 需加一行（见上） |
| LLM 传 `"60"` 而非 `60` | 不用管——`coerce_args`（`registry_v3.py:74`）按 JSON Schema 自动强转 |
| 工具抛异常 | 被 `registry.execute` 的 `except Exception` 接住，转成错误字符串回灌 LLM（不 crash agent） |
| ctx 尾参忘了写 | 不用 `ctx` 的工具可以不写尾参；需要的工具忘了写会 `TypeError: got unexpected keyword 'ctx'`——PythonExecutor 注入 ctx 时报错 |

## 本章小结

V3 的工具系统把「是什么 / 谁能调 / 怎么执行」三维正交分离：

| 维度 | 载体 | 职责 |
|------|------|------|
| **是什么** | `ToolSpec` + YAML（name/description/parameters） | 给 LLM 看的 schema |
| **谁能调** | `decide()` 三层叠加（side_effects × mode × 规则修正器） | 权限决策 |
| **怎么执行** | `ToolExecutor` + 4 执行器 | 实际副作用 |

**零 langchain 依赖**——整个 Tier 2 没有任何 `langchain` / `langgraph` import。工具从 YAML 声明到 OpenAI JSON 到执行器到权限决策，全部自研。
