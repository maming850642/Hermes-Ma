## 8.1 config.py 核心机制

| | |
|---|---|
| **文件** | 根目录 `config.py`（~87 行） |
| **取代** | V2 早期 `src/config.py`（pydantic-settings + `.env`，~190 行） |

### _Settings —— 双访问设计（`config.py:20-30`）

```python
class _Settings(dict):
    def __getattr__(self, name):
        try:
            return self[name]
        except KeyError:
            raise AttributeError(f"config key not found: {name}") from None
    def __setattr__(self, name, value):
        self[name] = value
```

> **双访问**：属性访问 `settings.llm_model_name` 对新代码自然；字典访问 `settings["llm_model_name"]` / `settings.get(...)` 对需要默认值或 `in` 判断的老代码兼容。`_Settings` 是 dict 子类，不依赖 pydantic。

### get_settings —— @lru_cache 单例（`config.py:33-84`）

```python
@lru_cache
def get_settings() -> _Settings:
    with open(PROJECT_ROOT / "config.yaml", encoding="utf-8") as f:
        cfg = yaml.safe_load(f) or {}
    # env 覆盖（只覆盖已有键）
    # OPENAI_API_KEY/BASE_URL 反写 os.environ
    # 数值键强转 int
    return _Settings(cfg)

settings = get_settings()   # 模块级常量，import 即可用
```

## 8.2 三个关键细节

### ① env 只覆盖 cfg 已有键（`config.py:49-62`，Bug 7 修复）

```python
for key in list(cfg):                          # ★ 只遍历 cfg 已有键
    env_val = os.environ.get(key.upper())
    if env_val is None: continue
    # ... 坏注入防御 ...
    cfg[key] = env_val
```

> **为什么只覆盖已有键？** 原逻辑用 `os.environ` 反向扩展键集合，会把 `PATH` / `TEMP` / `HOME` / `PYTHONPATH` 等全部以小写键塞进 settings，导致被无关键污染、排查时易误导。现在**只对 cfg 中已存在的键做覆盖**，未知环境变量不进入配置。

**坏注入防御**：当 yaml 值是 `"ns/name"` 形式、env 值正好是去掉前缀的部分时判为坏注入（保留 yaml）。针对外部启动器曾注入截断过的 `EMBEDDING_MODEL` 值。

### ② OPENAI_API_KEY / BASE_URL 反写 os.environ（`config.py`）

```python
os.environ.setdefault("OPENAI_API_KEY", cfg.get("openai_api_key", ""))
os.environ.setdefault("OPENAI_BASE_URL", cfg.get("openai_base_url", ""))
```

> LangChain 的 `ChatOpenAI` 默认从 `os.environ` 读 key。`setdefault` 把 yaml 里的值回灌到环境变量（不覆盖已存在的），让 LLM 客户端无感。V3 的 `LLMClient` 显式传 api_key，这个反写主要为兼容遗留代码（记忆模块的 LLM 调用可能仍用 langchain）。

### ③ 数值键强转 int（`config.py:69-76`）

```python
_INT_KEYS = {
    "llm_timeout", "max_short_term_messages", "max_memory_results",
    "max_agent_iterations", "tool_loop_threshold", "compact_keep_recent",
    "compact_min_messages", "compact_summary_max_tokens", "fs_max_file_size",
    "shell_timeout", "shell_max_output_chars", "web_search_timeout",
    "web_fetch_timeout", "model_context_window", "compact_threshold_pct",
    "tool_timeout", "max_tokens",
}
for k in _INT_KEYS:
    if k in cfg and cfg[k] != "":
        try:
            cfg[k] = int(float(cfg[k]))    # "3.0" → 3
        except (TypeError, ValueError):
            pass
```

> **为什么强转？** yaml 里若带引号（如 `llm_timeout: '120'`）会被解析成 str，传给 `socket.settimeout` / `timeout` 比较时抛 TypeError。`_INT_KEYS` 集中强转。

## 8.4 多进程部署形态

### 进程拓扑

```
用户登录
   ↓
FastAPI 主进程（web_fastapi/main.py）
   ↓ subprocess.Popen（每用户一个）
worker 子进程（worker_process.py）
   ├─ MemoryManager（记忆）
   ├─ HermesAgentV3（agent）
   ├─ MCP 客户端（asyncio event loop 线程）
   ├─ stdout 写线程（daemon）
   ├─ stdin 读取线程（daemon）
   └─ SessionBucket 字典（多会话）
```

### 进程生命周期

| 阶段 | 触发 | 代码 |
|------|------|------|
| 启动 | 用户登录 → `get_or_create(user_id)` | `worker_manager.py:257-303` |
| 就绪 | worker 发 ready 信号（sync 写 stdout） | `worker_process.py:773` |
| 服务 | 接收 IPC 命令 → 调 agent → 推事件 | `worker_process.py` 主循环 |
| 销毁 | 仅登出/应用退出触发（无空闲回收） | `worker_manager.py remove/shutdown_all` |
| 退出 | `save_all_buckets` + `shutdown MCP` + 排空写队列 | `worker_process.py:773-833` |

### Windows 特别处理

- **UTF-8 强制**（`worker_process.py:26-29`）：`sys.stdout.reconfigure(encoding="utf-8")`，防 emoji 输出崩溃。
- **Git Bash 探测**（`shell.py:73-119`）：PATH → 常见路径 → git.exe 反推。
- **进程树杀**（`shell.py:176-205`）：Windows 用 `taskkill /T /F`，POSIX 用 `os.killpg`。

## 本章小结

V3 的配置体系三个核心设计：

1. **yaml 唯一真相源**——`.env` 已删除，所有配置集中在 `config.yaml`，`config.py` 读取 + `@lru_cache` 单例。
2. **双访问**——`_Settings(dict)` 子类同时支持属性访问和字典访问，兼容新旧代码，不依赖 pydantic。
3. **防御性强转**——env 只覆盖已有键（防污染）、`_INT_KEYS` 集中强转（防 TypeError）、坏注入检测（防外部启动器截断）。

部署形态是 **FastAPI 主进程 + per-user worker 子进程**，OS 级隔离所有全局状态。代价是进程数 = 并发用户数，适合 to-B 场景。
