# 06 · 流式韧性工程

> 流式系统涉及多方（浏览器、FastAPI、worker、LLM 端点），任何一方卡死都会拖垮整个链路。本章记录「各种异常下半流不崩」的韧性设计——每一个都是真实踩坑后修的。

## 6.1 Worker 子进程 —— stdout 写线程防管道写满

| | |
|---|---|
| **文件** | `web_fastapi/worker_process.py`（~833 行） |
| **核心行号** | `worker_process.py:62-118` |

### 问题（根因）

前端断开 SSE（切会话/关标签页）后，worker **无感知**，继续往 stdout 写事件。OS 管道 buffer 约 64KB，写满后 `sys.stdout.write` **永久阻塞**，导致 worker 对所有后续请求无响应——而父进程还复用这个「活着但卡死」的 worker，整个用户就废了。

```
浏览器关标签页
   ↓
FastAPI 端 SSE 流结束（但 worker 不知道）
   ↓
worker 继续推 token 事件到 stdout
   ↓
OS 管道 buffer 64KB 写满
   ↓
sys.stdout.write 永久阻塞（native syscall，Ctrl+C 都打不断）
   ↓
worker 主循环卡死 → 所有后续请求无响应
   ↓
父进程还复用这个 worker（它「活着」）→ 整个用户废了
```

### 解法（`worker_process.py:62-118`）

worker 不直接写 stdout，而是 put 到无界队列，由一个常驻 daemon 写线程异步写。管道满/关闭时，阻塞的只是后台写线程，主循环继续读 stdin、继续工作。

```python
_stdout_q: "_q.Queue[str | None]" = _q.Queue()    # 无界队列
_pipe_dead = threading.Event()                      # 管道死亡标志

def _stdout_writer():                                # 常驻 daemon 写线程
    while True:
        msg = _stdout_q.get()
        if msg is None: return                       # 关闭信号
        if _pipe_dead.is_set(): continue             # 管道已死，丢弃后续
        try:
            sys.stdout.write(msg); sys.stdout.flush()
        except Exception:
            _pipe_dead.set()                         # 标记管道死亡
            logger.error("worker stdout 写入失败，后续事件将被丢弃")

def _send(msg, *, sync=False):                       # 调用方：put 后立即返回，永不阻塞
    encoded = encode_message(msg)
    if sync: sys.stdout.write(encoded); sys.stdout.flush()   # 仅启动握手用
    else: _stdout_q.put(encoded)                             # 运行期事件走队列
```

### 精髓

- **无界队列** → 调用方（主循环）永远不会阻塞，事件最多被丢弃不会卡死逻辑。
- **daemon 线程** → 进程退出时自动回收，不需 join。
- **`_pipe_dead` 标志** → 一旦写失败就置位，后续事件全丢，避免反复尝试。代价是这个 worker 后续事件都看不到了，但主循环还能响应（比如能切会话），用户层面可恢复。

> **话术**：这是一个典型的「生产者-消费者 + 故障隔离」模式，把不可控的外部 IO 阻塞隔离到后台线程，保证核心逻辑永远可用。

### sync 模式的例外（`worker_process.py:98-117`）

启动期握手信号（ready / init error）用 `sync=True` 直接写 stdout，不走 daemon 线程。原因：daemon 线程可能被 OS 延迟调度，导致启动退化到 10s+（父进程等 ready 信号等不到）。sync 写保证启动握手即时送达。

## 6.2 Worker 子进程 —— stdin 读取线程 + inline command

### 问题

V2 旧架构 `for line in sys.stdin` 阻塞，chat 运行时权限切换 / role 切换拿不到锁超时——因为主循环在跑 chat，读不到 stdin 的轻量命令。

### 解法（`worker_process.py:131-214`）

常驻 daemon 线程 `_stdin_reader` 逐行读 → `_cmd_queue`（`worker_process.py:139-152`）。主循环在 `_drain_stream_events` 的**事件间隙**非阻塞 peek 队列：

```python
# _try_inline_command（worker_process.py:168-193）
_INLINE_CMDS = {"permission_mode_set", "role_toggle", "role_get", "permission_mode_get"}

def _try_inline_command(state):
    try:
        cmd = state._cmd_queue.get_nowait()
    except _queue.Empty:
        return
    if cmd["op"] in _INLINE_CMDS:
        _handle_inline_cmd(state, cmd)    # 直接改内存状态，立即响应
    else:
        state._cmd_queue.put(cmd)         # 非轻量命令放回队列等主循环
```

> **效果**：用户在 chat 运行时切权限模式 / 切角色，worker 在 ReAct 循环的 token 间隙就能处理，不用等整轮 chat 结束。这是 V3 相对 V2 的体验改进——V2 的 LangGraph 图运行时无法被外部命令打断。

## 6.3 per-user 子进程模型

| | |
|---|---|
| **文件** | `web_fastapi/worker_manager.py`（~324 行） |

### 常量（`worker_manager.py`）

```python
DEFAULT_TIMEOUT = 300.0      # 单条命令默认超时（LLM 调用慢给足时间）
```

> 2026-08 变更：`IDLE_TIMEOUT`/`IDLE_REAP_INTERVAL` 与 `_idle_reaper`
> 已随空闲回收机制一并移除——worker 常驻，不再有定时回收。

### 生命周期

```
用户登录
   ↓
WorkerManager.get_or_create(user_id)
   ↓ subprocess.Popen 启动 worker 子进程
   ↓ 等 ready 信号（60s 超时，每轮 _readline_with_timeout(min(remaining, 10))）
   ↓
worker 就绪，开始服务
   ↓
登出 / 应用关闭 → remove / shutdown_all
   ↓
进程退出：save_all_buckets + shutdown MCP + 排空写队列
```

### 为什么每用户一个进程

Agent 有大量**进程级全局状态**：
- `InterruptStore`（内存快照）
- 记忆模块的 contextvar（`_current_user_id`）
- MCP 客户端的 asyncio event loop 线程
- 记忆写锁

如果用线程或协程做并发，这些状态的隔离会非常脆弱——V2 早期就踩过「两个用户信息没隔离、似乎共用一个 LLM 客户端」的坑。子进程是 OS 级隔离，最干净。

> **代价**：进程数 = 并发用户数，不适合 C 端百万用户。面向海量并发用户时需改造为进程池或其他隔离模型。

## 6.4 Worker 锁超时降级 503

### 问题

流式期间 worker 长时持锁（最长 300s/轮）。如果这时用户切会话或查记忆，普通命令拿不到锁，不能无限等。

### 解法（`worker_manager.py:73-120`）

```python
def send(self, op, timeout=DEFAULT_TIMEOUT, lock_wait=5.0, **kwargs):
    if not self._lock.acquire(timeout=lock_wait):    # ★ 5 秒拿不到锁
        raise TimeoutError(f"worker {self.user_id} 忙（chat 进行中？）")
    try:
        # 发命令 + 收响应
        ...
    finally:
        self._lock.release()
```

路由层把这个 `TimeoutError` 转成 **HTTP 503**，前端弹「AI 正在思考，请稍候」而不是 500 卡死。

### 绕过锁的三个特殊方法

| 方法 | 用途 | 为什么不走锁 |
|------|------|------------|
| `request_cancel()`（`worker_manager.py:181`） | 紧急发送 `chat_stop` | 推理期间锁被 `send_stream` 占用，直接写 stdin 插队 |
| `send_fire_and_forget()`（`worker_manager.py:202`） | 即时送达轻量状态变更 | 不等响应、不走锁，chat 期间也能送达 |
| `send_stream()`（`worker_manager.py:122`） | 流式版本，yield 事件 | 它是**持锁方**，其他 send 等 5 秒 |

## 6.5 IPC 层读阻塞防护

### _readline_with_timeout（`worker_manager.py:36-58`）

```python
def _readline_with_timeout(proc_stdout, timeout):
    q = _q.Queue()
    done_flag = threading.Event()
    def _reader():
        line = proc_stdout.readline()
        if not done_flag.is_set(): q.put(line)
    t = threading.Thread(target=_reader, daemon=True); t.start()
    try:
        return q.get(timeout=timeout)            # 主线程可控超时
    except _queue.Empty:
        done_flag.set(); return None             # 超时返回 None
```

> **同一个套路**：`proc.stdout.readline()` 会无限阻塞，所以用后台线程读 + 主线程 `queue.get(timeout)`。和双 deadline 硬超时是同一个模式——「把不可中断的阻塞丢后台线程，主线程用 Queue 可中断等待」。

## 6.6 FastAPI 纯转发层

| | |
|---|---|
| **文件** | `web_fastapi/routers/chat.py`（~70 行） + `web_fastapi/sse.py`（~15 行） |

### SSE 编码（`sse.py:10-12`）

```python
def encode_sse_event(event_type, data):
    return f"event: {event_type}\ndata: {json.dumps(data, ensure_ascii=True)}\n\n"
```

标准 SSE 两行格式：`event: xxx\ndata: {...}\n\n`。`ensure_ascii=True` 保持中文字节对齐测试稳定。

### chat.py 纯转发（`chat.py:34-48`）

```python
@router.post("/stream")
async def chat_stream(body: ChatRequest, worker: WorkerProcess = Depends(get_worker)):
    def event_gen():
        yield from _ipc_events_to_sse(worker, "chat", message=body.message, thinking=body.thinking)
    return StreamingResponse(event_gen(), media_type="text/event-stream")
```

**就这三行核心代码**——纯转发，零 agent 逻辑。`_ipc_events_to_sse`（`chat.py:19-31`）把 IPC 事件转 SSE：
- `event` → `encode_sse_event(event_name, payload)`
- `result` → `encode_sse_event("complete", ...)`
- `error` → `encode_sse_event("error", ...)`

### finally 必调 request_cancel（`chat.py:44-47`）

```python
@router.post("/stream")
async def chat_stream(...):
    def event_gen():
        try:
            yield from _ipc_events_to_sse(worker, "chat", ...)
        finally:
            worker.request_cancel()    # ★ 客户端断开也通知 worker 停止
    return StreamingResponse(event_gen(), ...)
```

> **为什么 finally 必调？** 客户端断开 SSE 时，FastAPI 的 StreamingResponse 会在下一次 yield 尝试时感知到（GeneratorExit）。`finally` 块保证无论正常结束、异常、还是客户端断开，都通知 worker 停止——避免 worker 对着无人读的 stdout 继续写（配合 6.1 的 stdout 写线程兜底）。

## 6.7 contextvars 专题 —— 跨线程状态传播的三个坑

> contextvars 是本项目最深的坑之一，出现三次（流式 LLM 线程、并发工具线程、per-user 工具隔离），每次的故障现象完全不同但根因相同，三个案例值得对照阅读。

### 坑 1：流式 LLM 线程丢 contextvar（双 deadline 硬超时的伴随坑）

**场景**：`stream_with_hard_timeout` 把 `stream_chat` 放进 daemon 工作线程。

**Bug**：裸 `threading.Thread(target=worker)` 不传播 contextvars。`user_id` / `vfs` / `depth` 拿不到 → 下一轮工具节点读 `get_current_user_id()` 拿到 None → 串号或崩溃。V2 还踩过一个更隐蔽的：LangChain 的 `var_child_runnable_config` 拿不到 → 污染共享 callback 状态 → 下一轮工具节点直接卡死（web_search 解码完 HTML 后整图无后续日志）。

**解法**（`llm_stream.py:70, 83`）：
```python
ctx = contextvars.copy_context()           # ★ 显式 copy
t = threading.Thread(target=ctx.run, args=(_worker,), daemon=True)  # ★ ctx.run
```

### ★ 坑 2：ThreadPoolExecutor 重入死锁（并发工具执行）

**场景**：多工具并发执行（web_search + read_file），用 `ThreadPoolExecutor` 起多个 worker 线程。

**Bug**（V2 commit 93f97c6，V3 保留同一坑的修复）：旧代码先创建一个 `ctx = contextvars.copy_context()`，然后所有 worker 都 `executor.submit(ctx.run, _run_tool, tc)`。看起来对——但 CPython 的 `Context.run()` **不可重入**：

```
worker 1 线程: ctx.run(_run_tool) → 进入 ctx → 在 httpx I/O 阻塞
worker 2 线程: ctx.run(_run_tool) → RuntimeError: cannot enter context: ... is already entered
                ↑ ctx 已经被 worker 1 "进入"了，CPython 不允许并发进入同一个 Context
```

worker 2/3/N 的 `_run_tool` 函数体**根本不执行**——不 put tool_start、不 put tool_end → 主循环 `while completed_count < N` **永远等不到** → agent 永久卡死。

**表象**：N 个并发工具只有 1 个有日志，其余静默无输出，agent 卡死无报错。**最难调的 bug 类型——静默失败**。

**解法**（`registry_v3.py:379-381`）：每个 worker 各自 `copy_context()`：
```python
def _submit(tc_item):
    cvars = contextvars.copy_context()              # ★ 每个 worker 自己 copy
    return executor.submit(cvars.run, _run_tool, tc_item)
```

> **话术**：`Context.run()` 是"进入→执行→退出"的同步语义，不是"获取引用"的并发语义。一个 Context 对象同时只能被一个线程 `run`。如果多个线程要用"同一份"contextvar 快照，必须各自 `copy_context()` 拿到独立副本——就像 `dict` 的浅拷贝。

### 坑 3：子 Agent 深度控制用 contextvar 而非 threading.local

`task` 工具嵌套调用时，用 `_current_depth` contextvar 做递归深度限制。

**为什么不用 `threading.local`**？因为 `task` 可能在 `ThreadPoolExecutor` 的并发路径里执行。`threading.local` 是 per-thread 的，新线程里是全新空状态（depth 重置为 0），不继承父线程的值 → 并发子 agent 各自看到 depth=0 → 绕过深度限制。

`contextvars` 经 `copy_context()` 正确传播父线程的值，且 per-worker 独立可写。

### 三个坑的共同根因

| 坑 | 场景 | 表象 | 根因 |
|---|---|---|---|
| 1 | 流式 LLM daemon 线程 | 下一轮工具节点卡死 | 裸 Thread 不传播 contextvar |
| 2 | 并发工具 ThreadPoolExecutor | N 个工具只有 1 个有日志，agent 卡死 | Context.run 不可重入，共用一个 ctx 死锁 |
| 3 | 子 agent 深度控制 | 并发子 agent 绕过深度限制 | threading.local 不跨线程继承 |

> **共同解法**：`copy_context()`。每个需要跨线程传播 contextvar 的地方，都显式 copy + `ctx.run`。V3 把这个模式应用在三处：`llm_stream.py:70`、`registry_v3.py:380`、`registry_v3.py:269`。

### 回归测试锁定 CPython 行为

V2 有三个测试组成防御网（`tests/test_contextvars_propagation.py`）——如果未来 Python 改了 contextvars 传播行为，测试会失败提醒：

| 测试 | 作用 |
|---|---|
| `test_threadpoolexecutor_does_not_propagate_contextvars_by_default` | **断言 bug 存在**——如果 Python 某天默认传播了，测试失败提醒 |
| `test_each_worker_gets_its_own_context_copy` | 验证隔离——一个 worker 的局部 set 不泄漏到另一个 |
| `test_remember_contextvar_is_real_one` | 防止有人把 remember 工具改回模块级 dict（重新引入跨用户串号） |

> **话术**：「断言 bug 存在」的测试很反直觉但很有价值——它锁定了一个你依赖的平台行为。如果平台修了这个"bug"，你的代码可能出问题，这个测试会提前告警。

## 6.8 turn_messages 增量回写协议

> 这是长任务前端状态同步的核心机制。

### 问题

ReAct 多轮迭代时，每轮会产生中间消息。如果每轮都全量回写 worker 的 session_messages，HITL resume 多次会重复累积历史。

### 解法（`worker_process.py:581-624`）

```python
def _drain_stream_events(state, req_id, stream):
    last_turn_count = 0
    for event in stream:
        etype = event.get("type")

        if etype == "turn_messages":
            turn_msgs = event.get("messages", [])
            if last_turn_count > 0:
                del state.session_messages[-last_turn_count:]  # 先删上一轮的临时增量
            state.session_messages.extend(turn_msgs)            # 再追加最新一轮
            last_turn_count = len(turn_msgs)
            continue  # 不转发前端

        if etype == "messages_snapshot":
            # 压缩后全量快照：整体替换 + 清零 last_turn_count
            state.session_messages = list(event.get("messages", []))
            last_turn_count = 0
            continue

        # 其他事件转发前端
        _send(make_event(req_id, etype, **event_without_type))

        if etype in ("complete", "human_approval_request"):
            break
```

**「先 del 再 extend」的幂等性**：resume 多次也不会重复累积历史。`last_turn_count` 跟踪上一轮写入数，下次先删旧再追加新。

### cancel 轮询

每收到一个事件检查 `_cancel_event`（`worker_process.py:588-590`）——用户点「停止」时 `_cancel_event.set()`，drain 循环在事件间隙 break。

## 本章小结

V3 流式韧性的七道防线：

| # | 防线 | 防的故障 | 机制 |
|---|------|---------|------|
| 1 | stdout 写线程 | 前端断开 → 管道写满永久阻塞 | 无界队列 + daemon 写线程 + `_pipe_dead` 标志 |
| 2 | stdin 读取线程 | chat 运行时无法收轻量命令 | daemon 读线程 + `_cmd_queue` + inline command |
| 3 | 双 deadline 硬超时 | vLLM 半开连接 / trickle-hang | daemon 工作线程 + Queue + gap/total 双 timer（02 章） |
| 4 | worker 锁超时降级 | chat 期间其他命令拿不到锁 | `lock_wait=5.0` → TimeoutError → HTTP 503 |
| 5 | IPC 读超时 | `readline()` 无限阻塞 | 后台线程读 + `queue.get(timeout)` |
| 6 | contextvars copy_context | 跨线程 user_id / vfs / depth 丢失 | 三处显式 `copy_context() + ctx.run` |
| 7 | finally request_cancel | 客户端断开 worker 不知道 | FastAPI finally 块通知 worker 停止 |

**共同模式**：「把不可中断的阻塞丢后台线程，主线程用 Queue 可中断等待」——出现在防线 1/2/3/5。

> **话术**：流式系统的韧性设计是本项目最难的部分。难点不在「让流跑起来」，而在「各种异常下半流不崩」——端点半开、前端断开、管道写满、跨线程 contextvars 丢失、并发工具死锁。每一个都是真实踩坑后修的。
