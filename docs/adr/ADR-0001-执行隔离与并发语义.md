# ADR-0001：执行隔离与并发语义

- 状态：Accepted（本 ADR 文档集构成 /dev-plan 的输入基线）
- 日期：2026-08-27
- 关联：审计报告 §2（全局状态与进程边界）、§3.1/§3.5（单执行者假设）、§6-4（风险排序）；ADR-0003（任务账本）、ADR-0004（进程拓扑）
- 对应 SLO：A「桌面单机档」（见 `docs/architecture.md`）

## 背景

审计报告 §3.1 描述的结构性现状：

1. **全局唯一 worker 子进程**。`WorkerManager.get_or_create` 把任意 user_id 归一为
   `LOCAL_USER`（`web_fastapi/worker_manager.py:284-286`），Popen 启动
   `python -m web_fastapi.worker_process`；worker 主循环单线程串行逐条取命令
   （`web_fastapi/worker_process.py:941-953`）。
2. **每 op 全程持锁，无排队语义**。`DEFAULT_TIMEOUT = 300.0` 是 chat 单轮持锁上界
   （`worker_manager.py:36`）；并发小命令 `lock_wait` 默认 5s 拿不到锁即抛 TimeoutError→503
   （`worker_manager.py:103-106`），SSE 路径 `send_stream` 5s 后直接 yield
   "AI 正在思考" 错误帧（`:148-150`）。第二个标签页发消息的结局是**一致拒绝**而非排队——
   审计 §6-4 将其列为高频体验痛点。
3. **stdout 单读者泵假设行不可分片**（审计 §3.5）：`_StdoutPump` 常驻读线程 + 队列
   （`worker_manager.py:43-75`），req_id 多路复用依赖顺序无损坏。
4. **任务型负载已有成功的解耦范本**：waker/wakerflow 由主进程调度线程发现到期后，
   fork `python -m src.wakerflow.worker_node` 子进程执行，带 600s 泵+队列+总截止
   （`src/waker/async_runner.py:290-306`、`src/wakerflow/executor.py:565-649`），
   与前台 chat **零锁竞争**。遗留例外：旧回退路径 `worker.send("waker_run")` 仍存在于
   `src/waker/scheduler.py:246-255`，会在 worker 进程内共享 agent 并改写全局 contextvars，
   属应清理的反面教材。

SLO-A 的并发语义要求：1 个前台 turn + 后台任务并行；第二个并发 chat **显式排队**而非静默拒绝。

## 决策

### D1：双层执行模型

| 层 | 承载物 | 内容 | 隔离手段 |
|---|---|---|---|
| 前台交互层 | 唯一常驻 worker 子进程 | chat turn、工具执行、HITL 往返、MCP 连接、会话桶 | 进程边界 + WorkerManager 锁 |
| 任务层 | 按需短命子进程 | waker run、wakerflow node、git clone、未来批量作业 | fork + 显式 timeout + RunRegistry 登记 |

前台继续由常驻 worker 承载的理由：会话桶、MCP 连接、InterruptStore、工具注册表等
进程内状态复用是现有正确性的来源（审计 §2 表格），拆散它们的收益为零、一致性代价极高。
任务层沿用已验证的 `worker_node` 范式（spawn → 硬截止 → 退出即回收），新任务类型一律走此通道；
禁止新增代码使用 `worker.send("waker_run")` 旧路径（清理项移交 /dev-plan）。

### D2：有界 FIFO 排队取代秒拒

`WorkerManager` 为 `send / send_stream` 增加等待队列：

- 小命令保持短等待（现 lock_wait=5s 语义不变，可配置）；
- chat 类请求进入 FIFO 等待，上限默认 ≤120s（可配置），期间向前端发送排队位提示
  （如 SSE `queue_position` 事件），超时才降级为明确错误；
- req_id 多路复用协议不变——排队只发生在「获取锁之前」，不改变 IPC 行格式，
  因此 `tests/test_web_fastapi/test_ipc.py` 锁定的消息构造器零改动。

实现细节（数据结构、公平性、取消传播）留给 /dev-plan。

### D3：取消语义维持协作式 + 双截止兜底

现状取消 = `_cancel_event` 在 `_drain_stream_events` 每事件间隙检查
（`worker_process.py:644-647`）；单轮 LLM 流内部不可中断，靠
gap timeout=`llm_timeout`(120s) + 总 deadline=3×（`src/agent/llm_stream.py:84-123`）兜底。
本 ADR 维持该分工：不做流内硬中断（openai SDK 无中断保证，收益不抵复杂度）；
但 D2 引入排队后，**取消必须校验作用对象是当前持有锁的请求还是排队中的请求**
（防止「取消误会成取消别人的请求」——详见 architecture.md 风险 7）。

## 备选方案与否决理由

按命令要求对比四候选：

| 候选 | 结论 | 评估要点 |
|---|---|---|
| 进程内线程池 | ✗ 否决 | Python GIL 下 CPU 型工作（大 JSON 解析、长文本拼接）互相拖累；工具段错误/OOM 的爆炸半径=整个服务；HITL 快照恢复依赖的进程边界被打破；超时无法可靠施加（线程不能安全 kill）。 |
| 按需子进程 | ✓ 采用（任务层） | 即现状 waker/flow 范式：IO/CPU 天然隔离（独立解释器）、超时=pump+队列+总截止后 kill 进程树、限额=进程级、爆炸半径=单次任务、复杂度已沉没成本。作为唯一前台层则冷启动延迟（60s ready 等待撞首 token P95≤2s）不可接受。 |
| 常驻子进程（每实体一个） | ✗ 否决（前台层维持全局一个） | ×200 项目内存不可控；连接/桶寻址/SQLite 写竞争全面升级（违反 SLO-A「桌面档」复杂度预算）；每实体 ready 语义与懒加载冲突。**注意并非全盘否决**——若未来升 SLO-B（操作并行档），这是第一演进方向。 |
| 容器 | ✗ 否决 | 引入 Docker 违反「单机零外部服务」约束；Windows 开发机不作容器假设；对内存型单用户应用收益趋零。 |

## 回滚成本

- D2 排队器是 WorkerManager 内聚改动：特性开关关闭即回到「秒拒」旧行为，IPC 协议未动，前端提示可降级忽略。成本低。
- D1 本质是现状的超集（正式化既有事实 + 封禁一条遗留反路径），无数据迁移、无接口变更。几乎零成本。
- D3 维持现状，无回滚面。

## 验证方式（上线后怎么知道这个决策是对的）

1. 双浏览器标签页同时发起 chat：第二个收到排队位提示并在前者结束后自动开始，
   全程无 503/“AI 正在思考”（SLO-A 核心体验断言）。
2. `kill -9` worker 后下一次请求 ≤10s 内自动重建完成，历史消息从事件库投影完整恢复。
3. 任一 waker 任务运行中（最长 600s），前台 chat 发消息不被拒绝、互不感知延迟。
4. 新增回归测试：send_stream 在锁被占且排队≥N 位时的排队位事件序列；
   取消请求携带非当前执行 req_id 时不误停他人。
