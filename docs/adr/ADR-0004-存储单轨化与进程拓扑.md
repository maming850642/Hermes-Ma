# ADR-0004：存储单轨化与进程拓扑

- 状态：Accepted（本 ADR 文档集构成 /dev-plan 的输入基线）
- 日期：2026-08-27
- 关联：审计报告 §2（全局状态表）、§3.2/§3.3/§3.6（非原子写与盲写）、§5（幽灵会话与无 TTL）、§6-2/§6-3（风险排序前列项）；ADR-0001/0002/0003
- 对应 SLO：A「桌面单机档」——已落盘消息零丢失、events ≤10 万条、重启 RTO ≤10s

## 背景

探查核实的事实（含实测数字）：

1. **最热写路径是非原子整文件覆盖**：`save_session` 先读旧文件取 created_at/name/waker
   （read-modify-write，`src/session_store.py:279-292`），再 `open("w") + json.dump`
   整文件覆盖（`:315-316`）。而原子写范式在同仓三处成熟存在
   （`src/memory/file_store.py:96`、`src/waker/store.py:53`、`src/wakerflow/store.py:190`
   ——tmp + os.replace），唯独最热的会话路径没用。
2. **双写者竞态**：主进程 fork API 直接 `save_session(...)` 写 stub
   （`web_fastapi/routers/sessions.py:213-214`），worker 轮末 `_save_bucket` 写同一 sid 文件
   （`web_fastapi/worker_process.py:754` 一带）——两个进程、同一文件、互不知晓。
   审计 §6-5 将其列为低概率×中半径。
3. **SQLite 卫生缺失**：连接参数 WAL + busy_timeout=5000ms + synchronous=NORMAL
   （`src/storage/sqlite_provider.py:159-161`）；模块级 `_LOCK` 只保护进程内
   （`:50`）；全仓无 wal_checkpoint 调用。实测 `hermes.db` 572K 而 `-wal` 已膨胀至
   2.6M（4.6×）。purge 只有显式删会话一条路（`:459-467`）→ events/interrupt scope 永不清。
4. **幽灵空会话工厂仍在运行**：worker 启动即建随机 sid 空桶（`worker_process.py:288-290`）、
   reset 也新建空桶（`:828-841`）、退出 `save_all_buckets` 把从没用的空桶照样落盘
   （收尾路径 `:884-892`）。本次审计期实测 local 用户 184 个快照 177 个 messages=[]。
   list_sessions 半截/空 JSON 静默塞占位记录（`session_store.py:431-439`）与之互相放大。
   （注：存量数据用户已手动清空；此处治理的是**繁殖机制本身**。）
5. **状态分层真相**：messages 可从 events 表确定性重建；todos/vfs/waker 仅存于 JSON 快照；
   prefs/permission_mode 完全易失（重启复位）。schema 只有版本守门无迁移机制
   （`sqlite_provider.py:177-179`）。

## 决策

### D1：save_session 改 tmp + os.replace 原子写

同卷 rename 在 Windows/Linux 上均具平台保证；文件格式与读取路径完全不变，
旧代码无感。消除断电/崩溃窗口产生的半截 JSON，同时斩断 list_sessions 塞占位记录的输入源之一。

### D2：双写者收敛为单通道

fork 分支不再直写 `save_session`，改为经 worker_manager IPC 通道投递
（复用既有锁与队列语义）。写者唯一化后，「主进程/worker 各自 read-modify-write 同名文件」
的互覆面消除。若个别调用路径无法走通道（如 worker 未起），则退化为显式带锁封装而非裸写。

### D3：SQLite 卫生维护挂调度器

以 SchedulerService 注册项形态（衔接 ADR-0002 纪律①）定期执行：

- `wal_checkpoint(TRUNCATE)`：阈值触发（如 WAL > 2MB 或每 24h 兜底一次）；
- 陈旧数据清理：interrupt scope 中 resolved 事件的 TTL、事件总量逼近 SLO 上限
  （≤10 万条）时的最旧会话事件归档策略——参数 /dev-plan 定，机制此处定。

### D4：幽灵繁殖根治三点

1. worker 启动不再无条件创建随机 sid 空桶（懒创建：首个真实用户输入才建桶）；
2. 收尾 `save_all_buckets` 跳过 messages=[] 且 events 库亦无对应记录的桶；
3. `list_sessions` 对 messages=[] 且无事件的快照过滤兜底（防历史残留重新冒头）。

### D5：边车状态与拓扑取舍

- todos/vfs/waker 三项半持久状态本轮维持 JSON 快照承载（D1 原子化后其一致性大幅改善）；
  迁移至 kv/events 作为演进方向 B 记录，不在本轮实施（避免动摇投影不变量测试与
  load_session 事件优先路径的组合验证面）。
- prefs/permission_mode 易失复位列为**已知限制**明确写入文档；顺带修复机会（若 ADR-0005
  的 kv 改造顺手）另议，不做承诺。
- 进程拓扑维持两进程：FastAPI 主进程（路由/调度/账本/WorkerManager）+ 全局唯一常驻 worker
  （agent/工具/HITL/桶）+ 按需短命任务子进程（ADR-0001 任务层）。

## 备选方案与否决理由

| 候选 | 结论 | 理由 |
|---|---|---|
| 一步到位 SQLite 单轨化（todos/vfs/prefs 全迁库） | ✗ 本轮否决 | 改造面横跨 derive_messages 不变量、load_session 双路径、多个测试文件；收益集中在极少数崩溃场景。D1+D2 用 10% 成本拿掉 80% 风险。列为演进方向。 |
| 多 worker（按实体分进程池） | ✗ | SLO-A 无此诉求；模块级 _LOCK 进程内串行 + WAL busy_timeout 兜底下，多写者只会让吞吐被锁支配（审计 §2 两连接现实已证明协调成本）。 |
| 换 Postgres/Redis | ✗ | 违反单机零外部服务约束；当前库规模（<3MB）离任何嵌入式方案的性能悬崖都有一个数量级以上。 |
| 快照改事务型存储（SQLite 存 JSON blob） | ✗ 本轮 | 与上一条同理；os.replace 原子性已满足 SLO-A 的零丢失定义（丢 Windows 断电页缓存属 OS 层预算，见 architecture.md 风险 2）。 |

## 回滚成本

四项决策相互独立、可单独 revert：D1 无格式变化（纯写法替换）；D2 收敛后有兼容 fallback
分支描述；D3/D4 都是行为开关。唯一的「前瞻锁定」是把 project 字段留给 ADR-0005 定义在
快照 meta 内——任何回滚顺序下该字段都是可忽略的附加信息，向后兼容。

## 验证方式（上线后怎么知道这个决策是对的）

1. 压测：kill -9 于保存窗口反复注入（脚本循环 chat→kill），每次重启后
   `list_sessions` 无解析失败记录、无半截文件（D1 断言）。
2. 连续启停 10 次：data/sessions 零新增空快照；侧栏无点击必败条目（D4 断言，
   对照审计 §6-2 的最大可见面）。
3. fork 与轮末保存并发压测同 sid：消息计数单调不减、created_at/name 不互踩（D2 断言）。
4. WAL 尺寸长期稳定在阈值之下；events 总量可见且有归档动作发生（D3 断言）。
