# ADR-0002：调度模型

- 状态：Accepted（本 ADR 文档集构成 /dev-plan 的输入基线）
- 日期：2026-08-27
- 关联：审计报告 §6（时钟/休眠相关风险未列坏点＝现状已正确处理）；ADR-0001（任务层）、ADR-0003（RunRegistry）、ADR-0004（SQLite 卫生挂调度器）
- 对应 SLO：A「桌面单机档」

## 背景

模板要求评估「定时器堆 vs 存储到期扫描」并回答防拖累与补跑风暴。本项目现状**已经给出答案**
（探查核实）：

1. 触发者 = 主进程普通 daemon 线程 `SchedulerService`，单线程主循环以
   min(tick, 0.5s) 步长 `_stop_event.wait` 醒来比较到期项，到期提交到各注册项
   自己的 ThreadPoolExecutor（`src/plugins/scheduler_plugin.py:48-55, :204-243`）。
   当前三档 tick：waker 30s（`web_fastapi/app.py:133-145`）、wakerflow 30s（`:170-177`）、
   记忆聚合 300s（`:184-193`）。
2. next_run_at 持久化为 naive 本地墙钟 datetime（`src/waker/schedule_parse.py:10`；
   存储：waker.yaml state 节 `src/waker/scheduler.py:262-272`、flow state.json
   `src/wakerflow/scheduler.py:235-246`）。
3. **补跑语义已是「至多一轮」**：interval 类 overdue 则 compute_next_run 返回 now——
   下个 tick 立即跑一次不堆积（`schedule_parse.py:88-90`）；daily 当日窗口已过且未跑也返回 now
   （`:99-101`）。系统休眠恢复后第一轮 tick 补触发一次即归位。
4. **时钟回拨只推迟不重复**：due 判定用墙钟（is_due `schedule_parse.py:108-115`），
   服务自身计时用 monotonic——两者分工明确，回拨不会造成双跑。
5. **防单个实体拖累已有机制**：每注册项独立 ThreadPoolExecutor + running 标记去重
   （`scheduler_plugin.py:230-237`）、(uid,name) 防重入集合（`src/waker/scheduler.py:94-95, :183-188`）、
   `max_concurrent` 上限、单次运行 600s 硬截止（`async_runner.py:55`、`executor.py:54`）。

结论：这一层没有审计暴露的重大缺陷，本 ADR 的主要工作是**固化纪律、论证不改**。

## 决策

1. **沿用**「单调度 daemon 线程 + 到期扫描 + 注册项线程池提交」模型。
   规模依据：≤200 个定时实体时 30s tick 的 O(n) 扫描在 μs 量级，任何更精巧结构无可测收益。
2. **三条纪律**写入开发规范（供 /dev-plan 落实检查）：
   - 新定时需求只能注册为 SchedulerService 注册项，禁止裸起线程 / 自建 while-sleep 循环；
   - 每个注册项的每次运行必须带显式硬截止，并把 run 登记进 RunRegistry（衔接 ADR-0003），
     失败原因落账本供 UI 死信呈现；
   - 「计时用 monotonic、判定用墙钟」的分工不得混用（防回拨/休眠类 bug 的根基）。
3. ADR-0004 的 SQLite 卫生维护（wal_checkpoint 等）同样以 SchedulerService 注册项形态接入，
   不另起机制。

## 备选方案与否决理由

| 候选 | 结论 | 理由 |
|---|---|---|
| 外部 cron / systemd timer | ✗ | 引入外部服务/部署耦合，违反单机自包含约束；且丢失补跑语义的自定义能力。 |
| asyncio 时间轮/堆 定时器 | ✗ | 迁移现有 daemon 线程体系零收益；200 实体规模下堆 vs 数组扫描无可测差异。 |
| 每实体独立触发线程 | ✗ | 200 实体 × 独立线程不可控；拖累防护退化为每个线程自己负责，回到模板要防的原问题。 |
| 分布式调度（Redis/ZK 类） | ✗ | 单机单人桌面产品形态下是无意义的复杂度放大器。 |

## 回滚成本

纯保守决策（不改任何现行代码路径，仅新增注册项与规范）。无回滚面。

## 验证方式（上线后怎么知道这个决策是对的）

1. 制造 overdue：把机器睡眠跨过一个 daily waker 的目标时刻后唤醒——观察到恰好一次补跑，
   且下一轮 next_run_at 回到正常节奏（不连续双跑）。
2. 把测试环境某 waker interval 调到 10s 并令其持续失败：其他 waker 的触发节奏不受影响
   （防拖累断言），失败记录在 RunRegistry 可见（衔接 ADR-0003）。
3. 时钟回拨注入（手动改系统时间回拨 1h）：无重复触发，仅推迟到下一个合法窗口。
