# ADR-0003：任务状态与恢复

- 状态：Accepted（本 ADR 文档集构成 /dev-plan 的输入基线）
- 日期：2026-08-27
- 关联：审计报告 §2（进程边界表）、§5（无界增长）、§6-3（盲写覆盖）；ADR-0001（任务层）、ADR-0005（git clone 的 UI 呈现）
- 对应 SLO：A「桌面单机档」——恢复类指标：pending 审批跨重启存活、项目↔会话绑定持久、失败可观测

## 背景

项目里「任务」概念的真实现状：

1. **RunRegistry 已存在但覆盖面窄**：`src/waker/async_runner.py:89-92` 把 run 写穿到
   SQLite kv 表 scope="runs"，重启可见；启动时把残留 running 标记为 interrupted。
   但它只登记 waker/flow run——草图 1 引入的 git clone 等新任务没有账本。
2. **HITL pending 已是双轨且够用**：worker 内存 dict（thread_id→InterruptSnapshot）+ SessionLog
   durable 事件双写（`src/agent/hitl.py:99-168`），重启时 `recover_into` 回填
   （`web_fastapi/worker_process.py:389-397`）。审批不丢，主进程只是不可查询。
3. **无界增长提醒**（审计 §5）：runs 记录同样需要保留策略，否则成为下一个 events 无 TTL。
4. 会话 turn 本身不缺状态建模：真相源是 events 表 + `derive_messages` 投影
   （不变量被 `tests/test_session_log.py` 与 `tests/test_agent_events.py:302-318` 锁定）。

## 决策

### D1：升格 RunRegistry 为唯一任务账本

kv scope="runs" 的 value 扩展为统一结构：

```
{ kind, label, status, error?, started_at?, finished_at? }
status ∈ queued | running | done | failed | interrupted
```

- git clone 作为第一公民接入：主进程 spawn 子进程（**不经 worker 锁**）、显式 timeout；
  克隆目标先落临时名 `.clone-<run_id>`，成功后 rename 为最终 slug 目录，失败清理临时名
  并落 `failed` + error 字符串。死信呈现 = 入口页项目卡片上的失败徽标（对照草图 1），
  点开可见原因。
- 保留策略：done/interrupted 滚动保留最近 N 条（默认建议 100），failed 单独上限
  （默认建议 50），防 §5 式无界增长。具体数值 /dev-plan 定。
- 新增只读查询端点 `GET /api/runs`（增量 API，非破坏性变更）。

### D2：恢复策略 = 重启标记 interrupted，不做 lease/heartbeat

沿用 `async_runner.py:89-92` 的「启动期 running→interrupted」。理由：
单机两进程 + 任务子进程由父进程直接 spawn，父子生命周期天然可控；
lease+heartbeat 解决的是多执行器对同一任务的争抢，本项目不存在该问题，
心跳的定时器与判定复杂度没有对应爆炸半径可买。

### D3：裁剪说明——会话 turn 不建任务表

模板默认问「排队/执行中/完成/失败 任务如何建表」。本项目的会话 turn **不需要**：

- turn 的持久真相已是事件流（SessionLog events + JSON 快照），再造 turn 状态表是审计
  批评过的双轨形态重演；
- 「排队中/执行中」的前台瞬态由 ADR-0001 的 WorkerManager FIFO 队列承载，生命周期≤单请求，
  入库反而制造清理负担。

## 备选方案与否决理由

| 候选 | 结论 | 理由 |
|---|---|---|
| lease + heartbeat | ✗ | 见 D2——复杂度找不到匹配的故障场景；600s 级硬截止已覆盖悬挂检出。 |
| 固定超时兜底单用 | ✗ 不充分 | 只有超时无账本时，中断的任务在 UI 层凭空消失（正是「死信不可见」）。故超时保留 + 账本必需。 |
| 新建 tasks 表（替代 kv scope=runs） | ✗ 本轮否决 | kv 行级读写已满足量级（runs 是低频写入）；迁正式表的收益（索引/约束）要到 SLO-B 任务并发上量后才存在。列为演进方向。 |
| 失败静默重试退避 | ✗ | 任务多为用户显式发起（clone/waker），盲目重试可能放大副作用；重试策略留给具体任务类型自决并在账本记录 attempt。 |

## 回滚成本

- 账本结构扩展是纯增量：旧读者只认 status 字段即可工作；弃用新字段零损坏。
- 若放弃 git clone 任务化改走他途，删除 kind="git_clone" 的写入点即可，历史记录滚动过期自净。
- 低成本整体回滚：所有变更收敛在 RunRegistry 写入端与新端点。

## 验证方式（上线后怎么知道这个决策是对的）

1. 在 clone 进行中途 kill 主进程：重启后该 run 状态=interrupted，目标 slug 目录不存在
   （临时名已被清理或从未 rename），入口页无半成品卡片。
2. 构造必然失败的 clone（坏 URL）：账本出现 failed + 可读 error；入口页徽标可见；
   连续失败 N 次后旧记录按保留策略滚动。
3. runs 记录总量有界（压测 200 次 run 后行数 ≈ N 上限内）。
4. HITL 回归不受影响：审批 pending → kill worker → 重启 → approve 继续原 turn（现状能力保持断言）。
