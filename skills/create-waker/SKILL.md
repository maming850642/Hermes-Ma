# 创建数字员工（waker）与流程（wakerflow）

本技能教你把用户在聊天里说出的需求，落成一个真正会自动运转的数字员工或流程。
写入口只有四个工具：`list_wakers`（查现有）、`create_waker`（建员工）、
`set_waker_enabled`（启用/停用）、`create_wakerflow`（建流程）。
所有落盘都走这些工具——**绝不要试图用 bash 直写系统目录**，那会绕过校验，
产出永不调度或损坏的配置。

## 何时建议什么

| 用户表达 | 建议 |
|---|---|
| "每天/每周/每小时…自动帮我做 X" | 一个 waker，schedule_type=daily/interval |
| "盯着 X，一有变化就 Y" | 一个 waker（interval 高频）或带调度的 flow |
| "先 A 再 B，B 的结果给 C"（多步骤串联） | wakerflow（pipeline） |
| "同时做 A/B/C，汇总给我"（并行） | wakerflow（parallel） |
| 中途需要用户拍板的流程 | wakerflow（ask_user 节点） |

单员工能干的事别上 flow。不确定时先问一句用户预期。

## 标准流程

1. **查现有**：先 `list_wakers` 防重名；也许已有能直接启用的员工。
2. **补齐信息**：下面清单里推断不出来的才问，一次问全，别挤牙膏。
3. **起草并创建**：`create_waker`（系统会弹审批卡给用户确认全貌）。
4. **二次确认启用**：创建默认未启用。明确告知用户"已创建未启用"，
   用户同意后再 `set_waker_enabled(name, enabled=true)`。用户犹豫就让他去页面看看再说。
5. **交付说明**：告诉用户调度节奏、任务内容写在哪、随时可以说"停掉"。

## 需求澄清清单

- **做什么**：目标产出是什么？做成什么样算成功？
- **频率/时刻**：多久一次？固定几点？（用户说"上班时"就确认具体钟点）
- **输入**：读哪些文件/数据？在哪？
- **输出**：写到哪个文件？还是要通知？
- **权限（关键）**：任务要不要写文件/执行命令？要 → `permission_mode=full_access`，
  并明确告诉用户"该员工将以完全访问权限自动运行"；纯只读/搜索汇总 → `before_changes`。

## 权限模式（无人值守的生死线）

waker 是**无人值守**运行的，审批没人批——这是它和 chat 的本质区别：

| 任务形态 | permission_mode | 原因 |
|---|---|---|
| 要写文件/执行命令（日报、生成报告、整理归档） | `full_access` | before_changes 会卡审批，**每次运行必然 error** |
| 纯只读（搜索汇总、巡检、通知类） | `before_changes` | 无变更操作，审批模式兜底更稳 |

判断依据是 task_prompt 的动作（写入/保存/生成文件），不是用户的语气。
选了 `full_access` 必须在交付说明里明确告知用户并获其同意。

## 命名规范

`^[a-zA-Z0-9_-]{1,64}$`，小写英文短横线最佳。把中文意图翻成英文：

| 意图 | name |
|---|---|
| 每日写日报 | `daily-report` |
| 盯 GitHub 仓库动态 | `github-watch` |
| 周报汇总 | `weekly-summary` |

重名时在语义后加序号（`daily-report-2`），不要起无意义名字。

## task_prompt 写作规范（四要素）

给"新来的、看不到这段对话的员工"写工作交接单：

1. **检查什么**：读哪些文件/数据源（写清路径）。
2. **怎么处理**：步骤化描述。
3. **输出到哪**：明确的文件路径。
4. **成功标准**：什么样算完成（格式、长度、分节）。

反面例子："帮我看看项目写个总结"（范围、位置、标准全缺失）。
正面例子："读取工作区 README.md 与 TODO.txt，把进度日报写入
daily_report.md：不超过 10 行，分'已完成/进行中/风险'三节，只依据文件内容。"

## 人格三文件（可选，宁缺毋滥）

- `identity`（核心职责）：一两句，这个员工"是什么、为谁、干什么"。
- `persona`（工作风格）：语气、详略偏好。日报类员工常写"简洁、数据优先"。
- `bible`（红线）：绝不做什么（"不修改源码""不外发数据"）。
用户没提就不硬编，留空即可。

## wakerflow DSL

完整语法、模板变量与示例 → 用 bash `cat` 读 `resources/flow-dsl.md`。
要点：steps 里 `worker:` 引用**已存在的 waker 名**（先 list_wakers 确认），
步骤间用 `{{steps.步id.result}}` 传值；用户输入用 `inputs` 声明、
`{{inputs.名}}` 引用。保存后系统会提示引用了哪些员工、缺谁。

## 对话边界

- 这些是管理面操作，用户会看到审批卡——如实呈现，别在文本里替用户"默认同意"。
- 触发运行不归聊天管：手动跑一次去对应页面点触发，或等调度到点。
- 你自己（员工上下文）看不到这些工具，属正常设计：员工不造员工。
